# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Configure

```
python scripts/config-build.py -hc <host-config> -bt Release -bp build
make -C build -j$(nproc)
```

Host configs live in `host-configs/`. For local development, use `ubuntu-lsl.cmake`.
TPL paths are resolved in `host-configs/tpls.cmake`; set `${GEOS_TPL_DIR}` in the host config.

## Tests

```bash
# All unit tests (gtest)
cd build && ctest --output-on-failure

# Single test
ctest -R <test_name> --output-on-failure

# Build and run unit tests
cd build && make build_test test

# Integration tests (ATS)
cd build && make ats_environment && ./integratedTests/geos_ats.sh
```

MPI tests use `-x <nranks>` in their command and are registered via `geos_add_test` → `blt_add_test`. Integration test baselines are stored in a GCP bucket; log baseline changes in `BASELINE_NOTES.md`.

## Architecture

GEOS is an HPC subsurface simulation framework (carbon sequestration, geothermal) built in C++17 with MPI, targeting exascale systems via RAJA/CHAI for portable parallelism.

**Entry point:** [src/main/main.cpp](src/main/main.cpp) → `GeosxState::initializeDataRepository()` parses the XML input deck, builds the mesh and physics solver tree, then runs the event-based time loop.

**Data repository (Group/Wrapper system):** The central data model is a hierarchical key-value tree rooted at [dataRepository/Group](src/coreComponents/dataRepository/Group.hpp). Every object (mesh, solver, constitutive model) is a `Group` that can hold nested `Group`s and typed `Wrapper`s. This tree is the single source of truth — solvers read/write data through named paths in the repository, which drives automatic restart/checkpoint via CONDUIT/HDF5.

**Mesh (DomainPartition):** [mesh/DomainPartition](src/coreComponents/mesh/DomainPartition.hpp) is the top-level mesh container. A `DomainPartition` holds `MeshBody` → `MeshLevel` → `ElementRegion` → `ElementSubRegion`. Node, edge, and face data is stored in `NodeManager`, `EdgeManager`, `FaceManager`. The mesh is unstructured with support for conforming fractures, embedded fractures, wells, and particle methods.

**Physics solver catalog:** Solvers register themselves via `REGISTER_CATALOG_ENTRY( PhysicsSolverBase, <SolverType>, ... )` and are instantiated by name from XML. The solver hierarchy:
- `PhysicsSolverBase` — base class with timestep and nonlinear solve infrastructure
- `CoupledSolver` / `CoupledSolverBase` — sequential implicit coupling for multiphysics (poromechanics, reservoir+wells)
- Individual physics solvers: flow solvers ([fluidFlow/](src/coreComponents/physicsSolvers/fluidFlow/)), mechanics solvers ([solidMechanics/](src/coreComponents/physicsSolvers/solidMechanics/)), and coupled solvers ([multiphysics/](src/coreComponents/physicsSolvers/multiphysics/))

**CRTP solver templates:** Coupled multiphysics solvers use a CRTP/mixin pattern where a template base class (e.g., `DualContinuumPoromechanicsSolverBase<FlowSolver, FlowSolver, MechanicsSolver>`) inherits from its template parameters to combine flow and mechanics capabilities. An alias `m_solvers` tuples the sub-solvers together.

**Discretization methods:** FEM is in [finiteElement/](src/coreComponents/finiteElement/) with the element formulation library in `finiteElement/elementFormulations/`. FVM is in [finiteVolume/](src/coreComponents/finiteVolume/). The `NumericalMethodsManager` in [discretizationMethods/](src/coreComponents/discretizationMethods/) selects which scheme to apply per region.

**Constitutive models:** [constitutive/](src/coreComponents/constitutive/) contains material models (fluid, solid, relative permeability, capillary pressure, permeability, etc.). Models wrap property data onto mesh regions and are also registered in the object catalog for XML-driven construction.

**Kernel dispatch:** Solver kernels (assembly, flux, upwinding) are generated from `.cpp.template` files using JSON specs (`kernelSpecs.json`) and the `generateKernels()` CMake function. Templates use placeholder tokens substituted during configuration to specialize for different physics (e.g., single-phase vs. compositional, thermal vs. isothermal).

**XML input:** Problem descriptions are XML files in [inputFiles/](inputFiles/) and [examples/](examples/). The schema is auto-generated from the code. XML defines the mesh, solver(s), constitutive models, BCs/ICs, and events.

## Project Layout

| Path | Role |
|---|---|
| `src/main/` | `main()`, builds `geosx` executable |
| `src/coreComponents/` | All physics, mesh, constitutive, IO, and utilities — organized as ~20 CMake static libraries |
| `src/coreComponents/physicsSolvers/` | Physics solver sub-libraries (flow, mechanics, multiphysics, etc.) |
| `src/coreComponents/constitutive/` | Material constitutive models |
| `src/coreComponents/mesh/` | Mesh data structures (DomainPartition, NodeManager, etc.) |
| `src/coreComponents/dataRepository/` | Group/Wrapper data tree, restart/checkpoint |
| `src/coreComponents/finiteElement/` | FEM discretization and element formulations |
| `src/coreComponents/finiteVolume/` | FVM discretization |
| `host-configs/` | Per-machine CMake host configs with compiler/MPI/TPL paths |
| `inputFiles/` | XML input decks for various physics |
| `examples/` | Example XML inputs |
| `scripts/` | Build, test, and dev utility scripts |
